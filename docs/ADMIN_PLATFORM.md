# طرح پنل مدیریت لکسا: کنسول سوپرادمین و کنسول مرکز

نسخه ۱، ۲۶ مهر ۱۴۰۵ (۱۸ اکتبر ۲۰۲۶). این سند فقط طرح است و هیچ کدی را عوض نمی‌کند.

## ۱. حکم

پنل فعلی برای یک اپ آموزشی تک‌کاربره ساخته شده، نه برای پلتفرمی که مرکزها و دانشگاه‌ها رویش کار کنند.

- **سوپرادمین** بعد از ورود همان داشبورد دانشجو (درس‌ها و کتاب‌ها) را می‌بیند. پنل ادمین فقط از مسیر `#/admin` باز می‌شود و در آن چند عدد، جست‌وجوی کاربر، تأیید بازخورد هوش مصنوعی، ساخت استاد و تنظیم پلن مرکز هست. ماژول‌هایی که در همه‌ی کنسول‌های جدی (Google Admin، Microsoft 365، Canvas، Moodle) پایه حساب می‌شوند نیست: صف کارها، هشدارها، چرخه‌ی عمر مرکز، تعلیق و قطع نشست کاربر، نقش‌های جزئی ادمین، لاگ ممیزی قابل جست‌وجو، پشتیبانی «مشاهده به‌جای کاربر»، اطلاعیه، فیچرفلگ، حریم خصوصی و پشتیبان‌گیری.
- **مالک مرکز** فقط سه نقش ثابت دارد (مالک، مدیر، استاد) و تب‌هایش (استادها، محتوا، کلاس‌ها، دانشجوها، مقایسه، API، اتصال، تنظیمات) هیچ صفحه‌ی خانه، ساختار سازمانی (شعبه، دانشکده، گروه)، نقش سفارشی با دامنه، تقویم آموزشی، گردش تأیید و قفل نمره، اعتراض به نمره، نظارت بر استاد، گزارش دانشجوی در معرض خطر، اطلاعیه یا تنظیمات امنیتی ندارد.

خلاصه: با استاندارد بازار فاصله‌ی زیادی داریم. راه درست اضافه کردن چند دکمه نیست؛ باید سه چیز پایه ساخته شود و بقیه روی آن‌ها بنشیند:

1. **خانه‌ی وابسته به نقش**: هر کس بعد از ورود صفحه‌ی خودش را ببیند.
2. **مدل دسترسی جزئی با دامنه** (permission + scope) به‌جای سه نقش ثابت، هم برای ادمین‌های لکسا و هم برای مرکزها.
3. **لاگ ممیزی و حفاظ‌های عملیات حساس** (MFA، تأیید دونفره، تعلیق پیش از حذف) که از روز اول همه‌ی ماژول‌ها از آن استفاده کنند.

|---|---|---|---|

| چرخه‌ی عمر مرکز | وضعیت، پلن، سقف صندلی، انقضا | در انتظار، آزمایشی، فعال، مهلت، معلق، بایگانی، زمان‌بندی حذف | متوسط |
| کاربران | جست‌وجو، جزئیات، نقش سراسری | تعلیق، قطع همه‌ی نشست‌ها، ریست MFA، عملیات گروهی، خروجی | زیاد |
| نقش ادمین | فقط admin | نقش‌های جزئی و محدود به دامنه (Canvas، Blackboard، Brightspace، Stripe) | زیاد |
| ممیزی | جدول lexa_audit بدون صفحه | جست‌وجو بر اساس کنشگر، هدف، زمان، IP و خروجی (Supabase audit logs) | زیاد |
| پشتیبانی | ندارد | «Act as» با مجوز جدا و ثبت در لاگ (Canvas) | زیاد |
| اطلاعیه و فیچرفلگ | ندارد | اطلاعیه‌ی سراسری و هر مرکز؛ فلگ با هدف‌گیری و تاریخچه (Canvas، Vercel) | زیاد |
| حریم خصوصی | فراموشی آمار مطالعه | صف درخواست خروجی و حذف داده با تأیید (Moodle data privacy) | متوسط |
| ساختار مرکز | مرکز ← کلاس | مرکز ← شعبه/دانشکده ← گروه ← برنامه ← درس ← کلاس (Canvas، Blackboard، Brightspace) | زیاد |
| نقش‌های مرکز | مالک، مدیر، استاد | نقش سفارشی با دامنه‌ی زیرشاخه (Moodle Manager، Google OU، Brightspace) | زیاد |
| ترم و تقویم | ترم با کد | تقویم با مهلت ثبت‌نام، حذف و اضافه، ورود نمره، اعتراض (سما، گلستان) | زیاد |
| نمره | ورود نمره و معدل قبلی | پیش‌نویس ← ارسال ← تأیید ← انتشار ← قفل، با اعتراض (گلستان) | زیاد |
| گزارش | مطالعه، مقایسه، داشبورد | گزارش در معرض خطر با قاعده‌ی شفاف، خروجی زمان‌بندی‌شده (Brightspace Data Hub) | متوسط |
| استانداردها | API امضادار، اتصال CSV/REST | OneRoster، LTI 1.3، SAML/OIDC، SCIM (1EdTech، OASIS) | متوسط |

## ۳. اصل‌های طراحی (برای همه‌ی فازها)

1. **خانه بر اساس نقش**: ادمین پلتفرم ← کنسول عملیات؛ مالک یا مدیر مرکز ← خانه‌ی مرکز؛ استاد ← خانه‌ی استاد (کلاس‌های امروز، نمره‌های منتظر)؛ دانشجو ← همان داشبورد فعلی. کسی که چند نقش دارد با یک انتخابگر بالای صفحه جابه‌جا می‌شود و نقش فعلی همیشه دیده می‌شود.
2. **کمترین دسترسی**: هر عمل یک مجوز نام‌دار دارد (مثلاً `org.grades.approve`). نقش فقط مجموعه‌ای از مجوزهاست. دامنه یا کل مرکز است یا یک شاخه از درخت سازمانی. بررسی همیشه سمت سرور (RLS و RPC) است؛ مخفی کردن دکمه فقط ظاهر است.
3. **MFA و تأیید دوباره**: هر ادمین پلتفرم و هر مالک یا مدیر مرکز باید MFA داشته باشد (aal2، مثل فاز ۲). عملیات حساس (تعلیق مرکز، تغییر نقش مالک، باز کردن قفل نمره، خروجی کامل داده) تأیید دوباره و دلیل می‌خواهد.
4. **تأیید دونفره** برای عملیات مخرب سطح پلتفرم (حذف مرکز، حذف کاربر، اعطای نقش ادمین ارشد): یک نفر درخواست می‌دهد و ادمین دیگری تأیید می‌کند (Google multi-party approval). اگر فقط یک ادمین ارشد داریم، به‌جایش تأخیر ۲۴ ساعته با امکان لغو.
5. **تعلیق پیش از حذف**: مرکز و کاربر اول معلق می‌شوند، بعد بایگانی و بعد حذف زمان‌بندی‌شده با مهلت ۳۰ روز. پیش از حذف، هشدار برگشت‌ناپذیری و خروجی داده.
6. **ممیزی کامل**: هر تغییر با کنشگر، نقش و دامنه‌ی کنشگر، عمل، هدف، مقدار قبل و بعد (خلاصه)، دلیل، IP و زمان ثبت می‌شود. لاگ فقط افزودنی است و صفحه‌ی جست‌وجو و خروجی دارد.
7. **کمینه‌سازی داده**: ادمین پلتفرم به‌طور پیش‌فرض شماره و ایمیل را نیمه‌پنهان می‌بیند. نمره‌ها و پیام‌های داخلی مرکز فقط با «مشاهده به‌جای کاربر» دیده می‌شوند که دلیل، بنر، حالت فقط‌خواندنی و مدت کوتاه (۳۰ دقیقه) دارد.
8. **مرز مرکزها**: هیچ کاربر مرکزی داده‌ی مرکز دیگری را نمی‌بیند. همه‌ی RPCها `org_id` را از دسترسی کاربر بررسی می‌کنند، نه از ورودی.

## ۴. کنسول سوپرادمین (پلتفرم)

### ۴.۱ خانه‌ی عملیات (اولین صفحه بعد از ورود)

- **نوار هشدار**: مرکزهایی که انقضا یا سقف صندلی‌شان نزدیک است، اجرای ناموفق اتصال (فاز ۷)، خطای API بالا (فاز ۵)، کلید API نزدیک انقضا، درخواست‌های تأیید دونفره‌ی معوق.
- **کارت‌های KPI** با بازه‌ی ۷ و ۳۰ روزه و مقایسه با دوره‌ی قبل: کاربر فعال روزانه و ماهانه، مرکز فعال، دانشجوی سازمانی، ساعت مطالعه، آزمون‌های انجام‌شده، صندلی‌های پر در برابر خریداری‌شده، درخواست‌های API.
- **صف‌های کار**: درخواست استادی، درخواست ساخت مرکز، بازخورد هوش مصنوعی، محتوای گزارش‌شده، درخواست‌های حریم خصوصی، تیکت‌های پشتیبانی. هر صف تعداد و قدیمی‌ترین مورد را نشان می‌دهد.
- **جست‌وجوی سراسری** (کاربر، مرکز، کلاس، کتاب) و میان‌برهای سریع: ساخت مرکز، اطلاعیه‌ی جدید، تعلیق کاربر.
- **فعالیت اخیر**: آخرین ۲۰ رویداد مهم ممیزی.

### ۴.۲ ماژول‌ها

| ماژول | ضروری (نسخه‌ی اول) | بعداً |
|---|---|---|
| مرکزها | فهرست با فیلتر وضعیت و پلن؛ صفحه‌ی هر مرکز (خلاصه، اعضا، صندلی، مصرف، کلیدها، اتصال، لاگ)؛ چرخه‌ی عمر کامل؛ یادداشت داخلی | مهاجرت داده بین مرکزها |
| کاربران | جست‌وجو و فیلتر؛ تعلیق و رفع تعلیق؛ قطع همه‌ی نشست‌ها؛ ریست MFA؛ تغییر نقش با دلیل؛ عملیات گروهی؛ خروجی CSV | ادغام حساب‌های تکراری |
| ادمین‌ها و نقش‌ها | نقش‌های پلتفرم: ادمین ارشد، عملیات، پشتیبانی، محتوا، مالی، ناظر فقط‌خواندنی | نقش سفارشی پلتفرم |
| ممیزی و امنیت | جست‌وجوی لاگ، خروجی، ورودهای ناموفق، ادمین‌های بدون MFA | ارسال لاگ به سرویس بیرونی |
| پشتیبانی | «مشاهده به‌جای کاربر» فقط‌خواندنی با دلیل و بنر | تیکت داخلی |
| محتوا | صف بازخورد هوش مصنوعی (فعلی)، محتوای گزارش‌شده، کتاب‌های منتشرشده | نسخه‌بندی کتاب |
| اطلاعیه | سراسری یا برای یک مرکز، با بازه‌ی زمانی و شدت | پیامک و ایمیل |
| فیچرفلگ | روشن و خاموش برای همه یا چند مرکز، با تاریخچه | انتشار درصدی |
| پلن و صورتحساب | پلن، صندلی، انقضا، تاریخچه‌ی تغییرات | فاکتور و درگاه |
| حریم خصوصی | صف خروجی و حذف داده با تأیید و مهلت | سیاست نگهداری خودکار |
| سلامت سیستم | وضعیت Edge Functionها، اجرای cron، اندازه‌ی جدول‌ها | صفحه‌ی حادثه |

## ۵. کنسول مرکز (مالک و مدیران)

### ۵.۱ خانه‌ی مرکز

- **کارت‌ها**: دانشجوی فعال در برابر صندلی، استادها، کلاس‌های ترم جاری، ساعت مطالعه‌ی هفته، نمره‌های منتظر تأیید، اعتراض‌های باز، دانشجوهای در معرض خطر.
- **کارهای من**: کلاس بدون استاد، کلاس بدون محتوا، استادی که نمره را دیر وارد کرده، مهلت‌های نزدیک تقویم، دعوت‌های بی‌پاسخ.
- **نمودارها**: روند مطالعه و حضور، توزیع نمره در هر کلاس، مقایسه‌ی شعبه‌ها و گروه‌ها.
- **فعالیت اخیر مرکز** از لاگ ممیزی.
- **انتخابگر دامنه**: مدیر یک شعبه فقط شاخه‌ی خودش را می‌بیند و همه‌ی اعداد به همان شاخه محدود می‌شوند.

### ۵.۲ ساختار سازمانی

درخت با گره‌های قابل نام‌گذاری. پیش‌فرض برای دانشگاه: مرکز ← دانشکده ← گروه ← برنامه. پیش‌فرض برای مؤسسه‌ی آزمون وکالت: مرکز ← شعبه ← دوره‌ی آزمون ← درس. کلاس‌ها، استادها و دانشجوها به یک گره وصل می‌شوند و گزارش‌ها روی هر گره جمع می‌خورند.

### ۵.۳ نقش‌ها و ماتریس دسترسی

نقش‌های پیش‌فرض (قابل کپی و ویرایش): مالک، مدیر کل، مدیر آموزش، مدیر شعبه یا گروه، استاد، دستیار و مصحح، مسئول آزمون، مشاور، مالی و پشتیبانی، ناظر فقط‌خواندنی.

مجوزها (نسخه‌ی اول):

| مجوز | معنی |
|---|---|
| org.settings.manage | تنظیمات، برند، امنیت مرکز |
| org.units.manage | ساخت و جابه‌جایی گره‌های درخت |
| org.roles.manage | ساخت نقش و اعطای آن (هرگز بیشتر از دسترسی خود اعطاکننده) |
| org.members.manage | دعوت و حذف استاد و کارمند |
| org.students.manage | ساخت، تعلیق و ریست حساب دانشجو |
| org.terms.manage | ترم، تقویم و مهلت‌ها |
| org.classes.manage | ساخت درس و کلاس، تعیین استاد و ظرفیت |
| org.enroll.manage | ثبت‌نام، حذف و اضافه، لیست انتظار |
| org.content.publish | انتشار محتوا برای کلاس یا کل مرکز |

قاعده‌ها: مالک همیشه همه‌ی مجوزها را دارد و حداقل یک مالک فعال لازم است. هر اعطا دامنه (کل مرکز یا یک گره) و در صورت نیاز تاریخ انقضا دارد. اعطای نقش و تغییر مجوز در لاگ ثبت می‌شود.

### ۵.۴ عملیات آموزشی

- **تقویم ترم**: شروع و پایان، ثبت‌نام، حذف و اضافه، آزمون‌ها، مهلت ورود نمره، مهلت اعتراض. سیستم خودش این مهلت‌ها را اجرا می‌کند (مثلاً بعد از مهلت، ورود نمره بسته می‌شود).
- **درس در برابر کلاس**: «درس» قالب ثابت است (نام، کد، واحد، محتوای پایه، طرح نمره‌دهی). «کلاس» اجرای آن درس در یک ترم با استاد، ظرفیت و زمان است. کلاس‌های ترم بعد با یک کلیک از ترم قبل ساخته می‌شوند.
- **ثبت‌نام**: ظرفیت، لیست انتظار، پیش‌نیاز ساده، گروه‌های ورودی (cohort)، ثبت‌نام گروهی با CSV.
- **عملیات گروهی**: انتقال دانشجو بین کلاس‌ها، تعیین استاد برای چند کلاس، تعلیق گروهی.

### ۵.۵ گردش نمره و اعتراض (مطابق رویه‌ی گلستان و سما)

`پیش‌نویس ← ارسال‌شده ← تأییدشده ← منتشرشده ← قفل`

- استاد وارد می‌کند و می‌فرستد؛ مدیر آموزش یا گروه تأیید می‌کند یا با توضیح برمی‌گرداند.
- با انتشار، دانشجو نمره را می‌بیند و تا پایان مهلت می‌تواند اعتراض بدهد.
- اعتراض به استاد می‌رود؛ پاسخ و تغییر احتمالی نمره ثبت می‌شود و دوباره تأیید لازم دارد.
- بعد از مهلت اعتراض نمره قفل می‌شود. باز کردن قفل فقط با `org.grades.unlock`، دلیل و ثبت در لاگ.
- طرح نمره‌دهی: مقیاس ۰ تا ۲۰، نمره‌ی قبولی، وزن اجزا (میان‌ترم، پایانی، کلاسی).

### ۵.۶ نظارت بر استاد

بار کاری (کلاس، دانشجو، ساعت)، چک‌لیست آمادگی کلاس (محتوا، طرح درس، آزمون)، سرعت ورود نمره نسبت به مهلت، فعالیت در کلاس. نظرسنجی دانشجو از استاد در فاز بعد.

### ۵.۷ گزارش‌ها و دانشجوی در معرض خطر

- گزارش‌های آماده: حضور و مطالعه، نمره و توزیع، مقایسه‌ی کلاس‌ها و شعبه‌ها، فعالیت استاد، مصرف صندلی، مقایسه‌ی مطالعه و نمره (فاز ۶).
- **در معرض خطر** با قاعده‌های شفاف و قابل تنظیم، نه جعبه‌ی سیاه: مثلاً «کمتر از ۱ ساعت مطالعه در ۱۴ روز» یا «میانگین آزمون زیر ۱۰». کنار هر نام دلیلش نوشته می‌شود. اقدام (تماس مشاور، یادداشت) ثبت می‌شود.
- خروجی CSV و Excel و خروجی زمان‌بندی‌شده (هفتگی) برای مدیران.

### ۵.۸ ارتباط

اطلاعیه برای کل مرکز، یک شاخه یا یک کلاس با تاریخ شروع و پایان و تأیید خواندن (اختیاری). قالب پیام. پیامک و ایمیل در فاز بعد.

### ۵.۹ تنظیمات، برند و امنیت مرکز

لوگو، رنگ، نام نمایشی و دامنه‌ی اختصاصی (بعداً). اجبار MFA برای کارمندان، مدت نشست، سیاست رمز دانشجو، نمایش لاگ ورود. صفحه‌ی پلن و صندلی و مصرف (فقط خواندنی؛ خرید با لکسا).

## ۷. داده‌های جدید (طرح اولیه، SQL از 013 به بعد)

- `lexa_platform_roles(user_id, role, granted_by, granted_at)` و تابع `lexa_platform_can(perm)`. `lexa_is_admin()` فعلی معادل «ادمین ارشد» می‌ماند تا مهاجرت کامل شود.
- `lexa_orgs.lifecycle` با مقادیر pending، trial، active، grace، suspended، archived، deletion_scheduled و تاریخ هر تغییر.
- `lexa_user_flags(user_id, suspended_at, suspended_by, reason)` و RPC قطع نشست‌ها (روی `lexa_svc_revoke_sessions` فاز ۲).
- `lexa_admin_approvals(id, action, payload, requested_by, approved_by, status, expires_at)` برای تأیید دونفره.
- `lexa_support_sessions(id, admin_id, target_user, reason, started_at, ends_at)` برای مشاهده‌ی به‌جای کاربر.
- `lexa_announcements(id, scope, org_id, unit_id, class_id, title, body, severity, starts_at, ends_at)` و `lexa_announcement_reads`.
- `lexa_feature_flags(key, enabled, org_ids, updated_by, updated_at)` و تاریخچه.
- `lexa_privacy_requests(id, user_id, kind, status, due_at, handled_by)`.
- `lexa_org_units(id, org_id, parent_id, kind, name, code, path)`.
- `lexa_org_roles(id, org_id, key, name, perms text[], is_system)` و `lexa_org_role_grants(org_id, user_id, role_id, unit_id, expires_at, granted_by)` و تابع `lexa_org_can(o, perm, unit)` که جای `lexa_org_can_manage` را به‌تدریج می‌گیرد. نقش‌های فعلی owner، manager و teacher به نقش‌های سیستمی نگاشت می‌شوند تا چیزی نشکند.
- `lexa_term_calendar(term_id, kind, starts_at, ends_at)`.
- ستون وضعیت گردش روی نمره‌های فاز ۳ و جدول `lexa_grade_appeals(id, grade_ref, student_id, reason, status, reply, decided_by)`.
- `lexa_risk_rules(org_id, rule, threshold, enabled)` و `lexa_interventions`.
- RPCهای خانه: `lexa_admin_home()` و `lexa_org_home(o, unit)` که KPI، هشدار و صف را در یک فراخوانی برمی‌گردانند.

همه‌ی RPCها مثل فازهای قبل: revoke و grant صریح، لاگ ممیزی، aal2 برای مدیران.

## ۸. فازبندی پیشنهادی

| فاز | محتوا | SQL | خروجی |
|---|---|---|---|
| A1 | خانه‌ی وابسته به نقش + کنسول عملیات سوپرادمین: خانه، مرکزها با چرخه‌ی عمر، کاربران (تعلیق، قطع نشست، ریست MFA، گروهی)، لاگ ممیزی | 013 | ادمین بعد از ورود کنسول را می‌بیند |
| A2 | خانه‌ی مرکز + درخت سازمانی + نقش سفارشی و ماتریس دسترسی با دامنه | 014 | مالک ساختار و نقش‌ها را خودش می‌سازد |
| A3 | تقویم و مهلت‌ها، درس و کلاس، کپی ترم، ظرفیت و لیست انتظار، cohort، عملیات گروهی | 015 | ترم کامل از ساخت تا پایان |
| A4 | گردش نمره، اعتراض، قفل؛ نظارت بر استاد | 016 | رویه‌ی رسمی نمره مثل گلستان |
| A5 | گزارش‌های مرکز، در معرض خطر، خروجی زمان‌بندی‌شده؛ اطلاعیه‌ها (پلتفرم و مرکز) | 017 | |
| A6 | حفاظ‌های پلتفرم: نقش‌های جزئی ادمین، تأیید دونفره، مشاهده به‌جای کاربر، فیچرفلگ، حریم خصوصی، سلامت سیستم | 018 | |
| A7 | استانداردها: OneRoster CSV، بعد OIDC و SAML، بعد LTI | 019 | |

ترتیب: A1 و A2 مستقیم دو ایراد اصلی را حل می‌کنند. A4 برای دانشگاه‌ها حیاتی است. A6 پیش از ورود ادمین دوم یا پشتیبان لازم است.

برای هر فاز همان روال فازهای ۱ تا ۷: فایل‌های جدید و SQL و سند با شاخه و PR؛ Z سیم‌کشی فایل‌های بزرگ (AppShell، router، OrgView، AdminView)، tsc، QA و انتشار.

## ۹. سؤال‌های باز

1. آیا ادمین دیگری غیر از خودت در لکسا خواهد بود؟ اگر نه، تأیید دونفره به تأخیر ۲۴ ساعته تبدیل می‌شود.
2. مشتری اول دانشگاه است یا مؤسسه‌ی آزمون؟ درخت پیش‌فرض و گردش نمره بر اساس آن تنظیم می‌شود.
3. پرداخت آنلاین داخل لکسا لازم است یا قرارداد بیرون از اپ بسته می‌شود؟
4. پیامک (مثلاً کاوه‌نگار) در نسخه‌ی اول لازم است؟
